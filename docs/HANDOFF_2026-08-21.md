## 1. Project Overview

xtraWork is a WhatsApp-first contract-change approval and evidence system for Indian construction and project businesses. Its core journey is:

1. An employee sends a WhatsApp message describing extra or changed work.
2. xtraWork authorizes the sender by phone, resolves the tenant and project, parses the request, and applies project access and cost/schedule limits.
3. The system creates a formal, versioned change request and sends the customer a private approval link.
4. The customer reviews and decides without creating an account.
5. The owner sees the result in the web dashboard and can retrieve an evidence package later.

The product is an approval ledger and evidence system, not an invoicing platform and not itself a licensed electronic-signature provider. It records secure-link assent and evidence that may help substantiate an agreement. The application deliberately does **not** claim that A0 secure-link assent is a government-recognised signature, that the underlying agreement is necessarily enforceable, or that the signer had legal authority. Those questions require contract-specific Indian legal advice.

## 2. Architecture / Framework / Setup

### System shape

xtraWork is a TypeScript `pnpm` monorepo implemented as a modular monolith. Three independently runnable processes share PostgreSQL and the same domain packages:

- `apps/web` — Next.js 15.1.4 and React 19. Owner dashboard, onboarding/settings, authenticated product UI, and public customer approval/receipt pages.
- `apps/api` — Fastify 5.2.1. Authenticated `/v1`, public `/public/v1`, and provider webhook `/webhooks/v1` HTTP APIs.
- `apps/worker` — background jobs and transactional-outbox consumers. Handles messaging, reminders, webhook normalization, media/file scanning, exports, evidence generation, integrity/retention work, and PDF rendering through Playwright/Chromium.

The dependency direction is intended to remain `domain <- application <- api/worker`; the web application consumes shared contracts rather than importing server internals.

### Shared packages

| Path | Responsibility |
| --- | --- |
| `packages/contracts` | Zod request/response schemas, error codes, events, assurance wording, signer-name validation |
| `packages/domain` | Money/tax, canonicalization and digests, state transitions, authorization policy, approval tokens, reminders, audit/evidence rules |
| `packages/application` | Auth, intake, change-request send/decision, OTP, public view, evidence, and other use cases |
| `packages/db` | PostgreSQL/Drizzle schema, SQL migrations, tenant-scoped repositories, units of work, jobs, outbox, idempotency, rate limits |
| `packages/integrations` | WhatsApp, email, OTP, Razorpay, managed identity, and provider adapters/webhook verification |
| `packages/files` | Local and S3-compatible private object stores, upload validation, quarantine, scanning |
| `packages/runtime` | Composition root and process wiring |
| `packages/observability` | Structured logs, redaction, metrics, request identifiers |
| `packages/testkit` | Seed data, fixtures, and real-PostgreSQL test harness |

### Data and infrastructure

- PostgreSQL 16 is the system of record; Drizzle ORM is used alongside explicit SQL where database semantics matter.
- Money is stored as integer minor units (paise) and quantities as decimal strings. Browser previews are never authoritative.
- Side effects use a transactional outbox and PostgreSQL-backed leased job queue with retry, backoff, and dead-letter behavior.
- Files and generated documents are private. Local storage is supported for development; S3-compatible storage is the production shape. The project has been configured for private Cloudflare R2, but credentials must never be copied into documentation.
- Email has been configured around SMTP/Resend for actual transactional delivery; local Mailpit/file outbox options remain available.
- Docker Compose can provide PostgreSQL, MinIO, and Mailpit. `infra/docker/Dockerfile` builds API and worker targets from the same application image.
- Supabase has been used as the hosted PostgreSQL/Auth environment during development. Application services are still primarily being exercised locally; a final public hosting topology has not yet been selected and deployed.

## 3. What's Been Built

### Identity, accounts, and onboarding

- Local password and email-link sign-in flows, browser sessions/cookies, CSRF protections, password hashing, and rate limiting.
- Google OAuth with state and PKCE when provider configuration is supplied.
- Registration email verification and user-facing handling for attempts to create a duplicate email account.
- Managed JWT identity-provider support for hosted auth configurations.

- Logout back to the public/sign-in experience.
- Tenant isolation is implemented through organization-scoped rows in a shared schema. A new account receives its own organization/business data context; the implementation does not create a physically separate database table per user.
- A testing-account setup script exists. There should be no general application-level email-verification bypass; the exact hosted database state of `test@gmail.com` must be checked separately.

### Owner web application

- Authenticated dashboard and navigation for projects, customers, employees, permissions, reports, inbound requests, settings, and change details.
- Logged-in UI received a dedicated visual redesign and responsive design pass; public/login work was intentionally not the initial design focus, although auth error states were subsequently corrected during debugging.
- Profile/business editing, logout, onboarding, loading/empty/error states, and account-oriented navigation.
- Change rows link to detailed information and provide evidence-pack download/preparation status.
- Reports aggregate approved changes and support CSV/report exports. The reporting path was corrected so an employee does **not** need a web account: any customer-approved request created through authorized intake is eligible to appear.
- Project-level evidence export now produces a genuine combined project evidence PDF rather than reusing or mislabelling a single-version document.

### Employee/WhatsApp intake

- Employee authorization by phone number without requiring an employee web login.
- Organization and project resolution, project grants, request ceilings, and fail-closed handling for ambiguous or unauthorized input.
- Structured and conversational intake support, including parsing compact message formats and asking for missing information.
- Durable intake provenance/checkpointing so retries can resume without creating duplicate change requests.
- Inbound media capture and private file handling.
- Simulator support for exercising the intake journey before a live WhatsApp rollout.
- WhatsApp Cloud API adapter, template handling, provider-message IDs, signature-verified webhooks, delivery-status normalization, reminders, and delivery ledger infrastructure are implemented. Live Meta rollout remains an external configuration and launch task.

### Change requests and customer approval

- Draft composition with local/server persistence, optimistic lock versions, authoritative server preview, and conflict handling.
- Cost, tax, schedule, ceiling, and permission validation.
- A send transaction reloads and locks canonical inputs, freezes a canonical JSON snapshot and digest, creates a private token, records audit events, and queues delivery.
- Sent versions are immutable. Revisions create a new version and supersede/revoke the prior one.
- Private no-account customer page with no third-party scripts, `noindex`, restrictive referrer/CSP behavior, and limited public projection.
- Approve, decline, and revision-request decisions with affirmative declaration, typed signer name, signed date, timestamps, and request metadata.
- A0 secure-link assent is the default. A1 OTP is supported when enabled. A2 licensed electronic signature is explicitly not implemented and cannot be silently substituted.
- Decision processing is atomic and idempotent; concurrent/replayed decisions have one winner.
- A decided link remains read-only and displays the agreed terms for 180 days, then stops resolving publicly while owner evidence remains retained.
- A successful customer decision queues a confirmation/receipt message. Per-recipient delivery state prevents a successful recipient from being resent merely because another recipient failed.

### Evidence, audit, files, and operations

- Append-only audit events with hash-chain verification and project/aggregate binding.
- Canonical frozen snapshots, content digests, terminal audit hash, attachment digests, and machine-readable evidence manifests.
- Version evidence PDF and combined project evidence PDF using the existing renderer.
- Evidence generation rejects a broken chain or a snapshot/digest mismatch instead of rendering unverified mutable data.
- Section 63-oriented certificate fields and honest explanatory wording are present. Generated certificates remain unsigned until the legally responsible people sign them; code does not invent those signatures.
- Private object storage, quarantine/scanning, bounded media downloads, image limits, retryable scanner outages, and retained quarantine for failures.
- Leased ownership for jobs, outbox records, file scans, and generated documents so a stale worker cannot complete work reclaimed by another worker.
- Razorpay webhook signature verification and monotonic amount/currency/status reconciliation.
- Health/readiness/metrics endpoints, deployment image, CI workflow, operational scripts, and runbooks for credentials, support access, backup/restore, audit verification, and replay.

## 4. Key Decisions Made

1. **Keep a modular monolith.** Web, API, and worker deploy separately but share domain/application packages and one transactional database. This preserves strong consistency while the product is still early.
2. **Use a shared multi-tenant schema, not one table/database per account.** Organization-scoped keys, foreign keys, repository operations, and authorization provide isolation without multiplying schema objects for every signup.
3. **Freeze what the customer saw.** Sending locks and reloads the draft, computes the canonical snapshot on the server, stores its digest/version, and makes later edits a new version. Evidence is generated only from that verified snapshot.
4. **Make PostgreSQL enforce critical invariants.** Tenant-bound foreign keys, state-transition triggers, append-only protections, uniqueness, leases, and transactional outbox behavior defend against application bugs and concurrency races.
5. **Keep provider calls outside database transactions.** Durable jobs/outbox entries make email, WhatsApp, PDFs, and scans retryable without holding database locks or reversing a committed approval.
6. **Store private approval capability minimally.** Approval-token records store hashes. Automated delivery temporarily carries an authenticated encrypted URL bound to tenant/version context and purges it after delivery. Receipt/access persistence remains hash-based.
7. **Customers do not need accounts.** The private token is the access mechanism; every decision and OTP operation revalidates live token state so an earlier public session cannot survive revocation.
8. **Employees do not need accounts either.** Authorization is based on the recorded phone/organization/project grants. Reports follow the approved change request, not whether the originating employee has a dashboard identity.
9. **Prefer honest assurance wording over claiming legal certainty.** A0 and A1 collect useful evidence; A2 is reserved for a licensed provider. Indian-law enforceability and Section 63 use still need counsel and human signatures where required.
10. **Retain decided customer links for 180 days, read-only.** This gives the customer a practical receipt window without exposing agreement details indefinitely. Owner-side evidence follows the organization's longer retention policy.
11. **Use the existing PDF renderer for project evidence.** The combined project pack is one genuine historical export, including relevant superseded/terminal versions, rather than a ZIP or a relabelled single document.
12. **Defer live automated WhatsApp rollout until configuration and operational readiness.** The adapter and correctness seams are being built now; Meta business assets, approved templates, public HTTPS webhooks, and real-device testing remain rollout gates.

## 6. Most Recent Work

Immediately before this handoff, local `pnpm dev` reached the web application but Next.js failed to compile `packages/contracts/src/api/change-orders.ts` with:

```text
Module not found: Package path . is not exported from .../zod
```

The problem was not the Zod import itself. A development-only block in `apps/web/next.config.mjs` replaced Webpack's package condition list with only `development` when the incoming list was undefined, dropping normal resolution conditions such as `import`, `require`, and `browser`. Production builds had passed because the override only ran in development.

The configuration now uses:

```js
config.resolve.conditionNames = ['development', '...'];
```

Webpack's `...` preserves its default conditions while prioritizing the development package export. The effective configuration printed `development,...`; web formatting and typecheck passed; the already running local site returned HTTP 200 at `http://localhost:3000`. No dependency update was needed. A non-blocking warning remains that Next's ESLint plugin was not detected and should be reviewed under the Medium/Low configuration cleanup.
