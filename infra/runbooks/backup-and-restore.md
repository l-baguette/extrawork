# Backups, health checks and restore rehearsal

Report §11.6 and launch blocker §16.3 ("Backups exist and one restore has been
completed").

## Schedule

| What                         | Frequency       | Retention            | Where                             |
| ---------------------------- | --------------- | -------------------- | --------------------------------- |
| Managed PostgreSQL PITR      | continuous      | 7 days minimum       | provider                          |
| Logical dump (`pg_dump -Fc`) | daily 02:00 IST | 30 days              | private object storage, encrypted |
| Object storage versioning    | continuous      | per lifecycle policy | bucket versioning                 |
| Backup health check          | daily           | —                    | alert on failure                  |
| **Restore rehearsal**        | **monthly**     | record the date      | isolated environment              |

PITR alone is not a backup strategy: it protects against corruption within the
retention window but not against losing the provider account. The daily logical
dump exists for that case.

## Taking a dump

```bash
./scripts/backup.sh
```

The script refuses to write an unencrypted dump and refuses to overwrite an
existing one for the same day.

## Daily health check

A backup that has never been restored is a hypothesis. The daily check verifies
the artifact is real, not just present:

```bash
./scripts/verify-backup.sh extrawork-YYYY-MM-DD.dump.gpg
```

It decrypts to a temporary file, runs `pg_restore --list`, and asserts that the
expected tables and a non-zero `audit_events` count are present. Alert if the
newest artifact is older than 26 hours (report §13.5: "backup freshness").

## Monthly restore rehearsal

Follow `restore-database.md` against a **throwaway** database, and record:

1. the artifact restored and its age,
2. wall-clock time from start to `readyz` (this is your real RTO — the report
   targets 8 hours for MVP and 2 hours in production),
3. the output of `pnpm db:verify-chain`,
4. the count from `project_integrity_mismatches()`.

Log the result in the launch-gate checklist. This is the evidence that closes
the §16.3 blocker; a rehearsal that was not recorded does not count.

## Restoring object storage

Evidence PDFs are regenerable from the database — the canonical snapshot is the
authority, and report §8.5 accepts that regenerated bytes may differ. Uploaded
originals are **not** regenerable. Bucket versioning is what protects them, so
verify it is enabled:

```bash
aws s3api get-bucket-versioning --bucket <bucket>   # expect Status: Enabled
```
